# r058-delete-empty-tag-tree 需求澄清

日期：2026-08-31

## 需求背景

首页侧栏的 Tags 区域展示层级 Tag 与笔记数，但无法清理不再使用的 Tag。用户需要在无关联笔记的 Tag 行上提供轻量、可发现且需二次确认的删除能力。

## 已确认决策

| 决策项 | 结论 |
| --- | --- |
| 数据源 | 仅支持 Supabase Direct；不实现或调整 Backend HTTP API。 |
| 数目语义 | Tag 行数目等于该 Tag 自身及全部后代关联笔记的总数。 |
| 删除资格 | 仅数目为 0 的 Tag 显示删除入口。若任一后代有关联笔记，父 Tag 数目大于 0，不可删除。 |
| 层级删除 | 删除数目为 0 的父 Tag 时，级联删除其全部后代 Tag；因此删除子树内的每个 Tag 均无关联笔记。 |
| 入口 | 指针悬停或键盘聚焦到可删除 Tag 行时，右侧数目位置显示垃圾桶图标。 |
| 确认 | 点击垃圾桶后显示应用内确认弹窗。确认提示只使用“确认删除 #work？”，其中 `#work` 替换为目标 Tag 完整路径。 |
| 非目标范围 | 不删除任何笔记或 note-tag 关联；不支持批量选择、Tag 重命名或 Tag 合并。 |

## 目标交互

```text
Tags
  # work                  0     ← 悬停/聚焦
  # reading                🗑
    # books                0

点击 🗑
┌ 删除 Tag ──────────────────────┐
│ 确认删除 #reading？             │
│                    取消  删除  │
└────────────────────────────────┘
```

## Supabase 契约确认

当前共享 schema 的 `tags.parent_tag_id` 外键为 `ON DELETE RESTRICT`，所以父 Tag 不能先于子 Tag 删除；实现必须按从最深后代到根 Tag 的顺序删除。`note_tags` 同样引用 Tag；数目为 0 的子树不含关联，因此删除不会触及 `notes` 或 `note_tags`。Supabase RLS 已授予认证用户对 `tags` 的 DELETE 权限，但删除时仍必须以当前 workspace 作为 scope。

## 验收标准

| 编号 | 标准 |
| --- | --- |
| A1 | 侧栏 Tag 行显示自身与全部后代的笔记总数。 |
| A2 | 只有数目为 0 的 Tag 在悬停或键盘聚焦时显示可访问的删除按钮。 |
| A3 | 数目大于 0 的 Tag 不显示删除按钮。 |
| A4 | 点击删除按钮后显示应用内确认弹窗，提示为“确认删除 #完整路径？”。 |
| A5 | 取消不改变 Tag 或筛选状态。 |
| A6 | 确认删除叶子 Tag 后，该 Tag 从侧栏与编辑器建议中移除。 |
| A7 | 确认删除空父 Tag 后，其所有空后代与父 Tag 都被删除。 |
| A8 | 删除请求失败时，乐观移除的 Tag 子树回滚并显示失败通知；不删除笔记。 |
| A9 | 若当前 Tag 筛选位于被删除子树内，删除成功后切回未选择 Tag 的状态。 |
