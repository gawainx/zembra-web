# FRONTEND

## 数据访问约束

- 前端主技术栈使用 `Vite + React + TypeScript + Tailwind CSS v4`。
- 前端数据访问通过 API Client 或 Repository 层隔离。
- UI 组件不得直接依赖 SQLite 表结构、migration 文件或 Supabase 查询实现。
- `vendor/zembra-schema` 只作为共享数据表契约来源，前端类型和 API DTO 需要围绕业务语义建立。
- Dexie.js 仅作为本地 demo、离线草稿或浏览器缓存的可选模块，不作为主数据库抽象。

## 依赖约束

- 前端仓库默认不引入 SQLite driver、ORM 或数据库 migration 运行时依赖。
- Supabase SDK 只在认证、实时订阅或明确直连场景中局部引入，不能在 UI 组件中直接铺开查询。
- 数据库、schema、同步和持久化相关依赖新增前，必须先核对 `docs/references/dependency-constraints.md`。
- Docker 和 Vercel demo 路径下的生产依赖需要保持轻量，避免引入大型 UI 套件和首阶段不必要的富文本编辑器。

## 通用 UI 实现规则

- 视觉修改前先确认参考实现或既有设计系统；禁止凭截图、经验或直觉猜测尺寸、颜色和控件行为。
- 每种视觉属性只能有一个权威来源：颜色来自主题 token，间距来自布局 token，尺寸来自语义尺寸 token。颜色遵循“物理 palette → 语义 token → 组件消费”的单向链路，组件不得直接写颜色值、颜色混合逻辑或主题例外。
- 布局责任按层级划分：页面负责区域，容器负责同级元素间距，表面负责自身内边距、边框和圆角，内容负责内部排版。禁止跨层通过 margin 补位置。
- 一个语义表面只保留一套轮廓表达；border、背景、圆角和阴影各自承担明确职责，禁止用 inset shadow 或叠加边框伪造层级。
- 富文本标记、标签、引用等内容必须按源数据位置和语义渲染，禁止为了 UI 实现而强制移位或改写内容结构。
- 纯图标控件的命中区只能由图标尺寸和统一命中扩展 token 推导；禁止写死点击框尺寸，也不得将文字控件的尺寸规则套用到图标控件。
- 所有视觉调整必须同时检查亮暗主题、相邻组件和溢出状态。测试只验证用户可观察行为、语义和交互结果，不断言固定颜色、尺寸、间距或 class 名称。
- UI 修改必须先向用户提供目标结构示意，完成后以实际界面验收，不以编译通过代替视觉正确。
